# Этап I.4 (закрытие) — Housing/migration, базовый XP, study-анимация

Источник: `Avanpost_GDD_v0.9.md`, разделы 2.2, 3.1, 5.4, 9.6, 17.3, 21.2–21.3 (строка 939), подтверждающие тесты 15 и 24.

## Что уже сделано (I.4, часть 1)

Сервер — источник истины по жителям: реестр `resident`, школы `gather`/`craft`, коммутативная
профессия (`Д→Добытчик`, `Р→Ремесленник`, `Д+Р→Каменотёс`), тики обучения `TRAINING_TICKS = 15`,
персистентность и идемпотентный replay. Клиент читает авторитетный снапшот, шлёт намерения
через единую очередь команд. Это закрывает критерий I.4 («профессия по обеим перестановкам»).

## Незакрытые пробелы I.4 (этот срез)

Три задачи, ровно по требованию заказчика и GDD:

1. **Housing Capacity и миграция.** GDD 3.1 (строка 172): Дом даёт «вместимость проживания,
   рост поселения». GDD 2.2 (строки 89, 91): новые жители прибывают естественно при
   достатке жилья и условий; спавн «каждые 30 секунд» заменён населением, зависящим от
   экономики и доступных мест. Тест 15 (строка 963): нет свободных домов — миграция не
   создаёт бесконечное население.
   Правило баланса: **+2 места за завершённый дом**; старт 3 жителя -> базовая ёмкость 3.
   Если `residents < capacity` — на тике `advance` приходит новый житель (визуально идёт к
   поселению — косметика серверного изменения реестра). Если `residents >= capacity` —
   миграция останавливается.

2. **Базовый XP от реальных задач.** GDD 2.2 (строка 83): «Навыки растут от выполнения
   реальных задач». Сейчас `xp` инкрементируется только на завершение школы (+1).
   Нужен настоящий источник: завершение работы (очистка клетки `ClearingCompleted`,
   завершение стройки `BuildingCompleted`, выдача ресурса из узла) даёт немного опыта
   тому исполнителю, который реально работал.

3. **§17.3 study-анимация.** GDD 17.3: житель за партой в школе, читаемая поза обучения.
   Базовый визуал: посадка за столом, лёгкое покачивание/карандашный цикл, подпись
   прогресса. Это представление состояния `studying` из снапшота, не новая механика.

## Архитектурная реальность (важно для планирования)

Реестр `resident` и рабочие сущности сервера (`laborer`, `clearing_job`, `building`) сейчас
**не связаны**: у `laborer` нет `resident_id`. «Реальные задачи» выполняют абстрактные
`laborer`-ы, а не жители. Значит для XP от задач нужно решить, как связать труд и жителя.

Варианты (см. решение D1 в отчёте ревью):
- **A (рекомендуется):** добавить `laborer.resident_id` (nullable). Назначение рабочего
  привязывает конкретного жителя; завершение реальной работы начисляет ему XP. Полный
  инвариант GDD 2.2 выполняется сразу, закладывает II.0 (житель переходит в войско).
- **B:** отдельная таблица-мост `resident_work_log` (кто, что, сколько). Гибче для аудита,
  но больше кода и миграций ради того же эффекта на этом этапе.
- **C (минимальный):** XP начисляется по роли/типу узла на владельца, не на конкретного
  жителя. Быстро, но не выполняет «навыки растут у жителя» — формально нарушает GDD 2.2.

## Зафиксированные решения (gstack eng-review)

- **D1 = A:** `laborer.resident_id` (nullable). Назначение рабочего привязывает конкретного
  жителя; завершение реальной работы начисляет XP ему. Опыт принадлежит личности, готовит II.0.
- **D2 = A:** каждый прибывший житель = 1 `laborer` роли `carrier`. Ёмкость жилья совпадает с
  числом рабочих мест, панель населения показывает одну честную цифру.
- **D3 = A:** XP-кривая 100 / 200 / 400 / 800 (быстрый рост, видно в демо и GIF).

## Принятый объём (после решения D1)

Контент и баланс:
- `content/population_balance.yaml` (P0, GDD строка 1105): `housing_capacity_per_house: 2`,
  `base_capacity: 3`, `starting_residents: 3`, `migration_enabled: true`,
  `migration_min_ticks: N` (задержка между прибытиями).
- `content/buildings.yaml`: у `house` явно `housing_capacity: 2` (или берём из
  population_balance по категории `housing`).

Сервер:
- Расчёт `housingCapacity = base_capacity + housing_capacity_per_house × (завершённые дома)`.
- На тике `advance`: если есть свободное место и прошёл `migration_min_ticks` — создать
  жителя (имя/таланты детерминированно по индексу, `profession='Разнорабочий'`), событие
  `ResidentArrived`. Если мест нет — не создавать.
- XP-хуки: `ClearingCompleted`/`BuildingCompleted`/выдача из узла начисляют XP исполнителю
  (согласно D1). События `ResidentXpGained` с `residentId, amount, reason`.
- Снапшот: `population: { capacity, residents, freeSlots, migrationEnabled }`, каждый
  житель несёт `xp`, `level`, прогресс до следующего уровня (простая кривая).

Shared/протокол:
- `WorldSnapshot.population`, поля жителя `xp` уже есть; добавить `level`, `xpToNext`.
- `ErrorCode` при необходимости (например `NO_HOUSING` — если решим ручное приглашение; в
  этом срезе не требуется).

Sim:
- `packages/sim/src/population.ts`: чистая `housingCapacity(finishedHouses, balance)`,
  `nextResidentIndex(residents)`, кривая XP `levelFor(xp)` / `xpToNext(xp)`.
- Тесты: ёмкость, остановка миграции при заполнении (тест 15), монотонность XP-кривой.

Клиент:
- Панель населения: «Жителей X / Y», счётчик свободных мест, прогресс-бар XP у жителя.
- Визуал: прибывающий житель идёт к поселению (косметический маршрут), XP-движение.
- §17.3: анимация «за партой» — поза сидя, покачивание, индикатор прогресса обучения.

Доказательства:
- Новый GIF-цикл: дом заполняется жителями (миграция идёт, потом останавливается при
  заполнении), житель учится за столом (анимация), XP растёт от выполненной работы.
- Скриншоты desktop/mobile, e2e-тест на миграцию и XP.

## Инварианты приёмки

1. Нет свободных домов -> число жителей не растёт (тест 15).
2. Завершённый дом строго увеличивает `capacity` на `housing_capacity_per_house`.
3. Новый житель проходит те же инварианты, что стартовые: строки в `resident`, валидная
   профессия, детерминированные имя/таланты.
4. XP растёт только от реально завершённой работы, не от простого тика.
5. Профессия по-прежнему коммутативна (регресс I.4 части 1 сохраняется).
6. Все мутации — через сервер; клиент только рисует снапшот и шлёт намерения.
7. `typecheck`, `build`, `test`, `e2e` зелёные; играбельный UI и доказательства на каждом шаге.
