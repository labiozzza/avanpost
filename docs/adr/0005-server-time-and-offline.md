# ADR 0005 — серверное время и офлайн-симуляция

Дата: 2026-10-21. Статус: принято для стабилизации I.5 (замена модели «клиент задаёт тики»).

## Контекст

До стабилизации клиент шёл `POST /api/commands/advance { ticks }` каждые ~0,4 с, а
`?fast=1` множил количество запрашиваемых тиков — клиент фактически управлял скоростью
экономики (D01). Офлайн-прогресс отсутствовал: закрыв вкладку, игрок останавливал мир
(D02). Часть систем применяла N тиков пакетной арифметикой (D07): разбивка одного периода
на несколько вызовов давала другие промежуточные моменты (крафт стартовал до прихода
ингредиентов).

## Решение

Единица времени — игровой тик. Реальный темп задаёт только сервер: `tick_ms` (конфиг
`AVANPOST_TICK_MS`, по умолчанию 400 мс = 2,5 тик/с, как в текущем игровом темпе).

- `world_state.last_simulated_at` — момент, до которого мир точно «посчитан» по тикам.
- Любой аутентифицированный вызов (`/api/state`, `/api/session`, любая команда) сначала в
  транзакции с `SELECT … FOR UPDATE` считает `due = floor((now − last_simulated_at) /
  tick_ms)`, обрабатывает `min(due, max_catchup_ticks)` тиков по одному, двигает
  `last_simulated_at += обработано × tick_ms` и `world_state.tick`.
- Остаток периода сохраняется в `last_simulated_at`; тихой потери длинного офлайна нет.
  Бюджет ограничивает стоимость одного HTTP-запроса, а не мировое время.
- Клиент не посылает тики: `AdvanceCommandSchema` без `ticks`; endpoint остаётся как
  «синхронизация» — сервер сам решает, сколько тиков прошло. Повторные и параллельные
  вызовы, две вкладки дают один результат (замок + монотонная `last_simulated_at`).
- Симуляция всегда обрабатывает по 1 тику (`advanceStep`), поэтому состояние зависит
  только от числа тиков, а не от разбиения периода (свойство эквивалентности A3).
- Идемпотентность: `request_id` команды логируется как раньше; повтор того же
  `request_id` не обрабатывает тики заново (`replayed=true`).
- Контроль часов в тестах: `AVANPOST_TEST_TIME_CONTROL=1` включает dev/test-роут
  `/api/test/set-clock` (сдвиг управляемых часов). В production флага нет — маршрут не
  регистрируется. `?fast=1` влияет только на локальные множители анимации клиента:
  время и экономику не трогает.

## Альтернативы

- Фоновый планировщик (cron/worker): требует инфраструктуры, той же точности per-tick
  шага и не даёт выигрыша в точности. Отложено до масштабирования игры.
- Пакетное свёртывание длинных периодов (`elapsed × rate`): отклонено — нарушает
  гейт-условия (приход сырья, дефицит, полнота буферов, смена занятости жителей).
