# ADR 0002 — Реестр мира и детерминированный регион

Статус: принято (этап I.1).

## Контекст

Для региона нужны согласованные правила рельефа, биомов, стоимости секторов и расчистки. Числа должны меняться без правок кода, а клиент не должен дублировать игровые правила. Рельеф каждого сектора должен воспроизводиться по seed и не храниться целиком в отдельном генераторе.

## Решение

1. Все параметры мира находятся в `content/world_balance.yaml`. Сервер загружает файл один раз, валидирует zod-схемой и отдаёт клиенту производный `catalog` в снимке.
2. `world_state.world_seed` — корень мира. Seed сектора вычисляется как `mixSeed(world_seed, sector_x, sector_y)`, биом выбирается детерминированно по весам, рельеф генерируется тем же seed. В БД хранятся seed и biome сектора для воспроизводимости.
3. Проходимость не персистится. Граф строится из клеток открытых секторов при сборке снимка для двух транспортов: `person` и `cart`.
4. Расчистка — это задание с `work_done`/`work_required`; работу добавляет команда `advance`, а не отдельный таймер. Завершение меняет тип клетки по правилу `becomes`.
5. Статус сектора выводится из состояния: активная расчистка → `clearing`, есть достижимые клетки → `prepared`, иначе `unlocked`. `unknown`, `unlockable`, `occupied` зарезервированы.

## Последствия

- Балансировка не требует пересборки клиента; достаточно обновить YAML и перезапустить сервер.
- Клиент рисует рельеф по каталогу и не содержит цветов/правил, кроме аварийных fallback-значений.
- Снимок растёт вместе с числом открытых секторов: 64×24 клетки на сектор. Для этапа I это приемлемо; при росте региона потребуется кеш достижимости и, возможно, дельта-снимки.
- Изменение формулы seed или весов биомов меняет уже открытые сектора при пересчёте. Поэтому seed и biome сектора сохраняются, а формула считается частью версии баланса.
